Project / simulation architectureCoDa / RAMSES-CUDATON

Constrained Cosmic-Dawn radiation hydrodynamics: RAMSES handles gravity/hydrodynamics while CUDATON accelerates radiative transfer on GPUs. Particularly relevant to the Atlas Local-Universe → Cosmic-Dawn bridge.

GADGET-4 for dark-matter and neutrino runs; AREPO for full hydrodynamics. This distinction is now explicit rather than treating MillenniumTNG as a single-code project.

Public coupled-dark-energy snapshots and catalogues. Production used a modified GADGET TreePM implementation; no canonical public GitHub production-code repository has been assigned here.

Observation ↔ simulation bridge

Uranometria's spatial views and cosmic timeline should be able to compare measured objects and structures with predictions from the simulation genealogy while keeping their epistemic status distinct.

Observation
Telescope/instrument catalogue, image, spectrum, redshift, position and uncertainty.
Selection
Apply the same redshift, luminosity, mass, wavelength and survey-selection window to observations and models.
Simulation
Query matching snapshots, lightcones, halo/galaxy catalogues or emulator predictions.
Comparison
Overlay distributions, abundance, clustering, morphology, environment and evolutionary tracks — never silently substitute simulated objects for observed ones.

LRD example: select an observed Little Red Dot at z≈4–10 → retain its telescope/catalogue provenance → open the same epoch on the cosmic timeline → request comparable simulated galaxies from Cosmic-Dawn runs → compare abundance, stellar/black-hole properties, colours, clustering and environment.

Local-cosmology example: select the Local Group, Virgo, Great Attractor or surrounding flow field → retain distance/redshift/peculiar-velocity provenance → compare against constrained Local-Universe simulations such as CLUES/CoDa and against statistical ΛCDM or alternative-cosmology ensembles.

Shared comparison contractObserved object ↔ epoch ↔ coordinate/scale ↔ selection function ↔ model run

The bridge should use stable IDs and provenance rather than copying simulation data into the observational catalogue. A comparison record can point to an observation, simulation project/run/snapshot, transformation or selection rule, metrics, uncertainty and rendering product.

Mobile simulation architecture

The Atlas should not attempt to ship production simulation volumes to a phone. It should expose progressively richer representations of them.

L0 · Catalogue
Project, cosmology, run parameters, provenance and links only.
L1 · Preview
Static thumbnails, tiny point samples and precomputed summary curves.
L2 · Interactive proxy
LOD tiles, halo/galaxy catalogues, slices, merger trees and emulator outputs.
L3 · Browser model
Reduced WebGPU/WebGL experiments such as 2LPT or quasi-N-body evolution.
L4 · Remote full run
HPC/server simulation stays off-device; the phone receives selected products or streamed visualization.

This makes the mobile interface a scientific control surface, not a miniature supercomputer. Emulators such as BACCO and CosmicEmu are especially valuable because they compress expensive simulation campaigns into fast parameter-to-observable predictions.

Recursive improvement bridge

The simulation catalogue can become a bounded evaluation domain for R1 without allowing R1 to rewrite the scientific baseline.

Candidate
R1 proposes a viewer, LOD, cache, scheduling or exploration-policy change.
Contain
Run it outside frozen P0 and against fixed simulation fixtures.
Measure
Mobile load time, memory, frame rate, bytes transferred, scientific error and provenance completeness.
Record
Trackinizer stores candidate → run → metrics → artifacts → decision.
Promote
Only improvements that beat the frozen baseline under explicit thresholds become candidates for human approval.

Replay pre-screening is appropriate for scheduling, selection and exploration-policy changes. Changes that alter prompts, context, simulation products or tool-visible inputs require real contained runs rather than stale replay outputs.
